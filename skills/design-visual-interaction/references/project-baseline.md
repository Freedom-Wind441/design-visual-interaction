# 项目基线

## 适用条件

新项目、缺少规范，或对“应当保留什么”存在冲突。已有完整基线的小修改直接复用，不另造设计系统。

## 目标与约束

建立本项目的共同语言，允许风格、平台和组件角色不同。不要将特定应用的业务字段、导航数量、品牌色或实验材质写入通用默认值。

## 依赖与联动

先查主题、组件库、资源与已有设计记录；只在具体问题涉及时读组件模块。公共 token 或共享组件归属有疑问时协作架构技能。

## 实施

### 从源码提取，沿消费者回溯

1. 先确认实际渲染栈；从本次组件的样式/构造函数出发，追踪主题包装、资源引用、运行时更新及局部覆盖，不只搜索常量名称。
2. 在相关源码范围用 `rg` 定位候选：Web 的 `var(--`、`:root`、`theme`；Android 的 `?attr/`、`@color/`、`Theme`、`Typography`、`dp`；Apple 平台的 `Color`、`Font`、`Environment`、样式结构。按实际技术栈缩小搜索，不整库倾倒结果。
3. 为受影响的颜色、字体、间距、圆角、动效记录下表。动效同时追踪 duration、easing/spring、减少动态效果分支；字体包括回退与缩放，颜色包括状态和主题覆盖。
4. 再沿调用点确认代表消费者，比较解析后有效值。主题别名不同可能指向同一来源，同名 token 也可能被局部覆盖；有重复字面量不等于应当全局合并。

| 语义/类别 | 定义位置与标识 | 值/单位或解析路径 | 主题/状态/覆盖 | 本次消费者 |
| --- | --- | --- | --- | --- |
| 主要操作前景/颜色 | 实际源文件与符号 | 引用链到最终值，无法解析则标未知 | 明暗/禁用/局部样式 | 具体组件及调用点 |

项目已有 token / theme 系统时，**必须优先复用，禁止新建平行体系**。缺项在原有体系中按现有命名补充；迁移系统仅在用户明确要求或可靠修复确有必要时提出有界方案，不借局部修复启动第二套颜色、字体或动效配置。

### 留下最小记录

在现有记录内补必要字段；无长期维护需求时用任务说明即可：

| 字段 | 内容 |
| --- | --- |
| 产品与环境 | 用户任务、平台/输入方式、窗口、内容密度、性能限制 |
| 设计来源 | 工程现状、明确认可的图/视频及版本、品牌与平台约束 |
| 公共规则 | 颜色/文字/间距/形状/动效 token 及源文件 |
| 组件规则 | 语义、状态、复用位置、必要例外 |
| 认可状态 | 稳定规则、试验参数、待确认效果分别标记 |
| 验证范围 | 可运行环境、代表页面、关键变化、覆盖缺口 |

将长期产品事实（用户任务、环境、约束）与可调整设计决策（颜色、密度、材质）分开；当前参数、目标提案与用户认可也分开。记录必要 token 时附语义、具体值/单位、来源文件与适用状态，不能从截图猜一个数值后当作实现事实。

复用项目已有设计记录，不强制文件名或另造真相源。公共规范决定默认规则；页面/组件例外只覆盖明确的目标、属性和状态，并注明原因，不能借局部例外改写全局。重新提取样式先比较现有记录，不覆盖已认可决策；跨会话只读取当前任务需要的部分。

新项目先选一条代表任务路径及其错误或空状态，依据内容与操作建立少量语义 token；不为未知未来生成完整组件库。无品牌偏好时采用适合平台的基础风格，注明可调整。

旧项目区分合理例外与漂移：危险操作、主要操作、选中导航和只读数据可以不同；相同语义且参数无理由分叉才是统一候选。比较截图记录窗口、主题、语言、字体、数据与版本。

## 验收

在变更 diff 与代表页面核对以下轻量检查；无关项跳过：

- 相同语义仍指向原 token 来源，没有新增平行主题或无解释的硬编码。
- 局部例外未泄漏到其他角色，公共修改已检查代表消费者。
- 明暗主题、字体回退/缩放、圆角/间距及动效语义沿用原语言；新增偏差说明原因。
- 用户认可、源码现状、候选参数分别标记；未运行部分仍列为未知。

能找到公共规则的唯一来源；代表流程遵循共同规则；例外有原因；未认可效果没有提升为标准；基线与当前代码一致。
