# 视觉与交互设计

## 职责与边界

将需求转为可实现、可检查的视觉与交互规则。默认改善项目内部一致性，保留合理差异；不把所有项目改成同一风格，不把代码整齐、编译成功或截图好看等同于体验改善。允许有证据地得出“不需修改”。

本技能是 `design-software-architecture` 的视觉与交互配套扩展，独立安装和使用，无硬依赖。涉及共享组件归属、状态所有权、平台适配或必要重构时协作：本技能负责体验目标，架构技能负责实现边界。普通参数修改不触发架构重写。

若 `reasoning-workflow` 可用，沿用其任务理解、证据和执行控制；它是独立第三方项目，仅引用，不复制或代为安装。配套技能不可用时继续完成能力范围内工作，不声称已经调用。

## 1. 确定本次范围

先读当前源码、工程约定（如 AGENTS.md）、设计规范、最近相关修改及可用截图/录屏。分开记录源码事实、实测现象、用户认可、设计假设和未知；历史实现不自动构成认可基准。缺少源码时仅做有界评估，缺少运行条件时说明验证缺口。

| 项目 / 请求 | 默认路径 |
| --- | --- |
| 新项目 | 按用途、平台、内容密度建立精简基线，先实现代表流程及异常状态 |
| 有一定规模 | 追踪到实际组件和调用点，先验证代表页面再推广 |
| 成熟项目 | 保留成熟规则，修复有证据的问题，允许零修改 |
| 仅改一个部位 | 以该部位及必要依赖为边界；检查共享消费者，不顺带重设计 |
| 审查 / 方案请求 | 交付诊断或方案，不擅自修改工程 |

在现有工作记录中简记目标、保留项、证据、拟读模块、影响范围和验收方法；小修改不新建流程文档。只有无法从工程推断的关键偏好才需询问；其余采用项目现有规则。

区分本次意图：技术审查检查可验证缺陷；设计评议判断任务重点、层级和表达；局部修复实施已定位问题；新建/重设计才建立新方向。自然语言即可选择，不要求特殊命令。完整优化可组合这些意图，但审查请求本身不授权实施；不要用代码规则替代审美判断，也不要用审美偏好冒充功能缺陷。

## 2. 公共基线与模块选择

始终遵守以下基线，不必加载所有模块：

- 项目已有 token / theme 系统时必须优先复用，禁止新建平行体系。沿实际组件追踪语义颜色、字体、间距、圆角及动效的定义与覆盖；缺项只在现有体系补充必要规则。相同语义保持一致，不强求不同角色外观相同。
- 同时处理可读性、状态、点击区域、焦点/可访问语义、非颜色提示及减少动态效果。采用目标平台规范，勿混用 px、dp、pt。
- 分开保存用户选择与运行时有效效果；能力不足时降级，勿覆写偏好。反馈不得伪造业务成功。
- 动画、阴影和折射不应阻挡输入、扭曲内容或破坏命中关系。
- 保留功能、状态含义、配置、导航历史及平台习惯；有明确要求或证据才改变信息架构。
- 区分根因：局部参数、重复组件、状态/事件、布局/字体、公共 token、平台限制。截图只证明现象，不能单独证明源码原因。

从下表选择最少的必要模块，通常为 1–3 个。“联动”是条件提示，不是递归加载命令；证据要求时才增加模块，不因“优化”就读取全部资源。

| 观察 / 任务 | 读取 | 需要时联动 |
| --- | --- | --- |
| 缺少基线，认可状态不清 | [项目基线](references/project-baseline.md) | 相关组件 |
| 新方向、页面平淡、主次混乱、密度或分组 | [构图与视觉层级](references/visual-composition.md) | 基线、排版、材质 |
| 技术栈/平台不清，或跨平台套用规则 | [平台适配](references/platform-adaptation.md) | 实际组件 |
| Dock、导航反馈或遮挡 | [Dock 与导航](references/dock-navigation.md) | 动效、排版 |
| 按钮、命中、按压卡住或重复触发 | [按钮](references/buttons.md) | 动效；必要时协作架构技能 |
| 字体、对齐、密度、翻译、大字号 | [排版与布局](references/typography-layout.md) | 受影响组件 |
| 滑块、数值、拖动冲突 | [滑块与数值输入](references/sliders-input.md) | 动效、设置 |
| 设置分组、条件选项、引导 | [设置与引导](references/settings-onboarding.md) | 导航、排版 |
| 动画、手势、回弹、振动 | [动效与反馈](references/motion-feedback.md) | 具体组件 |
| 主题、透明度、对比、模糊 | [颜色与材质](references/materials-color.md) | 排版、能力适配 |
| 用户明确要求实验液态玻璃，或修复已采用该材质的具体缺陷 | [可选实验：液态玻璃](references/style-liquid-glass.md) | 颜色与材质；涉及形变再读动效 |
| 需要对照可追溯的真实局部修复模式 | [公开案例](references/worked-examples.md) | 实际组件；不作为当前项目根因证明 |
| 实施后验收，或制定验证方案 | [验证与交付](references/verification.md) | 本次影响范围 |

默认在现有材质体系内优化；“现代化”“更好看”“通透”或平台支持模糊均不单独触发液态玻璃模块。修复既有玻璃也不授权推广到其他组件。

需要直观解释时查看[组件示意图](assets/component-anatomy.svg)。它是原则示意，不是品牌模板、认可实机效果或固定尺寸。

讨论主次和分组时可查看[任务层级示意](assets/task-hierarchy.svg)，只借助它理解信息关系，不照抄容器、位置或比例。

## 3. 实施最小充分修改

优先级：局部参数或事件 → 复用已有组件 → 修复共享根因 → 必要结构迁移。不为每个模块新建抽象层、依赖包或配置系统。公共规则归项目基线，组件保留角色差异。

用户限定范围时，先查共享实现的消费者；能局部解决则局部解决。若公共根因必须联动，说明证据和影响面；涉及用户明确禁止的区域时保持边界并说明未解决项，不静默扩张。

冲突时遵守用户当前要求、工程约定、功能正确性与可访问性；在此基础上保留已认可规范和平台语义。风格包不覆盖业务含义。允许由角色、平台或能力解释的差异。

需要实施时完成授权范围内修改。先在最能暴露问题的页面检查正常与异常状态，再推广共享规则。避免截图特判、硬编码机型、补丁叠加和隐藏文字掩盖根因；保持配置兼容和变更可逆。

外部设计资料、规则库和工具只在当前缺口确有需要时使用。先核对平台、版本、来源、许可和适用条件，记录引用或复用位置；不自动安装整套工具、循环抓取远程规则或带入无关风格禁令。项目私有源码与数据不得为了找参考而外发。检索结果或检查器命中是候选证据，不能自行升级为已确认问题。

## 4. 验证并收口

实施后读取验证模块，按改动选必要检查。区分静态审阅、可构建、事件通过、实际渲染通过、实机通过；只对取得证据的层级下结论。未见真实渲染，不宣称视觉通过；未执行交互，不宣称交互通过。

简要交付问题与根因、所选模块、实际改动与影响面、验证结果和未确认项。更新现有设计记录，区分稳定规则、试验参数与待定效果。无需每次输出完整清单，不承诺必然改善或固定比例的 token 节省。
